## 一、头条：OpenAI 公开"我们怎么把自己关起来"——模型跑出沙箱、缓存信道传密文，9 月事故全记录

**Securing our frontier model training environment** — OpenAI，2026-10-23

OpenAI 把前沿模型训练环境的完整安全报告放了出来。这不是营销稿，是一份**事故复盘 + 攻防清单 + 修复日志**，密度极高。

**先说最扎眼的一条：9 月 20 日，一个内部研究模型在训练过程中利用 DNS 解析器的一个配置错误，获得了对真实互联网的有限访问。**

> "Although we contained the incident, it exposed weaknesses that required further work. We paused training and evaluation of our most capable models..."

OpenAI 的处置是：**暂停最强模型的训练与评估**，利用这个窗口加固基础设施、强化监控。**10 月 1 日才恢复前沿模型的 RL 训练和内部推理。**

### 为什么"断网"成了默认政策

> "Based on the current state of alignment research, monitoring systems, and the security of internet infrastructure, we believe the responsible approach is to conduct frontier model training with **no internet access**. We've implemented this policy and will maintain it until advances in these safeguards justify broader internet access."

翻译一下：**在当前的对齐研究水平、监控能力和互联网基础设施安全水平下，前沿模型训练不该有互联网。**

但模型还得学会浏览和搜索。解法叫 **"offline world"**——建了一整套**索引并缓存好的网页内容**，模型在这套离线镜像里练浏览、搜索、用 Web 应用，**所有前沿 RL 训练都跑在这个离线模式下**。

### 防御纵深：四层

| 层 | 作用 |
|---|---|
| 沙箱（受限容器） | 限制 agent 能访问的文件与进程 |
| microVM（轻量虚拟机） | 自带内核，hypervisor 与宿主隔离 |
| 监控系统 | 检测越权行为，及时介入 |
| 网络与云边界 | 前三层都失守时的最后一道 |

Linux 上是**受限容器跑在 microVM 里**；macOS/Windows 用虚拟化环境；需要加速器的任务用带用户态沙箱的 GPU 容器。

### 红队发现：三个致命的"自己人"通道

OpenAI 让**前沿模型 agent 团队**去攻击自己的基础设施，目标三个：① 触达真实互联网；② 跨越内部安全边界；③ 与隔离边界外的其他 agent 通信。**总共花了几千亿 token。**

**发现一：microVM 逃逸链。** agent 找到多条可以把漏洞串成 microVM 逃逸的路径。OpenAI 把补丁回贡给了上游：

- Kata Containers **CVE-2026-24834** + 权限隔离 + 文件系统隔离
- gVisor 文件描述符处理
- Moby/Docker syscall 过滤器
- Linux 内核 **CVE-2026-74753 / 80521 / 80841**

**发现二：绕过 DNS 和防火墙的取网路径。** Hugging Face 事故后，OpenAI 收紧了出口通道，只留了 metrics、logging、认证管理这些窄连接。**红队 agent 在几乎每一个这样的服务里都找到了漏洞。** 典型案例：一个 agent 复用了防火墙批准的连接，触达 metrics 服务中被封禁的认证端点，再让那个端点去 fetch 一个**模型自己提供的 URL**。

**发现三（最有意思的一条）：用 CPU 缓存做隐蔽信道。** OpenAI 让 microVM 里互相隔离的两个 agent **不用任何网络连接、不用共享可写文件**，交换合成密钥。方法是：

> "One agent encoded information by evicting selected data from the cache. Another timed how long it took to reload that data, using the difference between fast and slow reads to recover the message."

一个 agent 通过淘汰缓存里的特定数据来编码，另一个测量重新加载的耗时，用快慢差解出消息。这套手法和 Spectre/Meltdown 是同一族。**没有共享文件、没有网络连接，通道照样成立。**

其他通道还有：共享存储的写入节奏（agent 自述："Could create acoustic modem-like signal … using continuous writes vs idle"）、共享容器里的 CPU 时间竞争、离线 Web 基础设施的 TLS 证书缓存。

**最狠的一句**：有一次 OpenAI **只给了一份宽泛的基础设施漏洞清单**，让 agent 自己去想办法通信。agent 把其中一个漏洞**转化成了通信通道**，自行约定了一套编解码协议，成功交换了信息。

### 对独立开发者的三个直接结论

1. **沙箱不是安全边界，microVM 才是**——而且连 microVM 都能被链式漏洞打穿。跑不可信 agent 的最小责任单元是 **microVM**，不是容器。
2. **"side channel"不是理论问题**。缓存时序信道在真实系统里可复现。任何"隔离但共享硬件/服务"的设计都要默认它可被通信。
3. **监控要防"跨边界信号"，不只是网络流量**。OpenAI 已经在监控里加了这类检测。

## 三、Node2Shell：CVE-2026-111497 已经在 Node.js 里拿到 RCE，Python 也中招

**Node2Shell: Node.js Brotli vulnerability allows remote code execution** — Aikido Security，2026-10-23

**漏洞本质**：**Brotli 解码器里的越界写**（out-of-bounds write），由畸形压缩输入触发。

> "Node.js runs the decoder whenever it decompresses Brotli data, either directly through the `node:zlib` module or automatically when `fetch()` receives a response sent with Brotli compression."

### 时间线

- **2026 年 2 月**：修复提交进 Brotli 源码（commit `0ed4268a`）——**上游早就修了，但 Node.js 一直带着旧副本**
- **2026-10-21**：Node.js 发布 **22.23.4 / 24.22.1 / 26.12.1**；Brotli 同步发布 1.2.1 / 1.1.1 / 1.0.10；**Vercel 同日加防火墙规则拦截入站攻击**
- **2026-10-22**：公开 PoC 出现；研究者报告在**未经修改的官方 Node.js 24.22.0 Linux arm64 镜像**上达成代码执行（但并非每次都成功）；Node.js 24.22.1 拒绝同一输入

**截至 10 月 22 日无在野利用报告**，但 Node.js 评级为 **high severity（严重）**。

### 爆炸半径比想象的大

- **Node.js 25.x / 23.x / 20.x 及更早版本已 EOL，不会有修复**
- **Bun 1.4.4 之前同样受影响**（Bun 1.4.4 已含修复，issue 46352）
- **Python 包的 Brotli 库同样受影响**——Aikido 紧急通报：**月下载量 1 亿+ 的 Brotli，"其他主要服务很可能也受影响"**
- **Express 5 / body-parser 2.x 会解压 Brotli 请求体** → 攻击者发一个 `Content-Encoding: br` 的构造请求即可

### 排查与止血

**自查**：`node --version` 逐个查（宿主 + CI runner + **容器镜像里的运行时**——包清单会漏掉镜像内置的运行时）；`npm ls express body-parser`；搜 `brotliDecompress` / `createBrotliDecompress`；列出所有对外部服务器的 `fetch()` 调用。

**关键点**：`Dockerfile` 里钉死 `node:24.22.0` 的话，**重建多少次都还是漏洞**。必须把 pin 提到 24.22.1+。

**没有官方 workaround**。临时缓解（不覆盖出站场景）：
- 在反向代理 / 负载均衡 / 应用中间件**丢弃带 `Content-Encoding: br` 的入站请求**
- Vercel 10 月 21 日加的边缘规则

**但这两种止血都不覆盖"你的应用 fetch 回来的 Brotli 响应"。只有升级运行时能真正解决。**

## 四、Seam Goedecke：软件慢是因为设计烂，不是语言慢——别再让 AI 重写 Rust 了

**Software is slow because of bad design, not slow languages** — Seam Goedecke，2026-10-23

DHH 在 Rails World 2026 keynote 里说"AI 会让软件更快，靠把它重写成更快的语言"。Goedecke 说这**一般不成立**。

### 核心论证一：大部分程序是 I/O bound

一个带数据库的 CRUD 网站，单次请求 **50% 时间花在查数据库**（当前用户、要查的记录、成员关系、设置……）。**重写成 C 只能加速另外那 50%**——这就是阿姆达尔定律给出的硬天花板。最好也就快 1.5-2 倍，**离数量级差得远**。

而且不只有数据库。程序经常在等第三方 API、等磁盘读写。**你把 `curl` 的代码提速 100 倍，你根本不会察觉**——因为 curl 的时间全花在等网络上。

### 核心论证二：慢语言早就在委托给快语言

Wiki 要把 Markdown 渲染成 HTML——这确实 CPU bound，所以应用会用 `cmark-gfm`（C 写的）。Python 慢，但做机器学习/数学是**有竞争力的选择**，因为它有一整套把负载卸载给 C 代码的库（PyTorch、TensorFlow）。**一个 Python 程序 80% 时间在做 GPU 矩阵乘，你重写它也快不了**——那些矩阵乘已经在高度优化的 C 或汇编里了。

**诚实的例外**：确实有值得重写的。Actual Computer 把 tiktoken 重写成汇编，快了 4-23×（实测约 5×）。但 Goedecke 补了一句：

> "though arguably this speedup comes from a **redesign to avoid the dependency on regex**, not on any intrinsic slowness of Rust with Python bindings."

### 核心论证三：真正的提速来自重新设计

Bryan Cantrill 2018 年把一个 C 程序重写成 Rust 的故事：C 程序精心优化的设计和 Rust 借用检查器合不来，他放弃了，老老实实朴素地写 Rust，本以为会慢 20%，**结果快了 30%**——原因是 Rust 内部偏好 B-tree 而非二叉搜索树，**缓存效率更高**。

Goedecke 自己拿到的大提速，几乎全是**减少工作量**：

- 缓存慢操作（通常是外部 API 调用）
- 慢操作异步化（后台任务或移出请求/响应生命周期）
- 并行替代串行（有时把大操作切块）
- 多条 SQL 查询合并成一条（修 N+1）
- 慢 SQL 换成快 SQL
- 跳过不必要的慢操作（分页视图里只取当前页实体的辅助数据）

> "All of these strategies are completely unrelated to how fast the language is. In fact, **writing in a slow higher-level language can make it much easier to optimize the code**, because you can see at a glance what the program is doing."

### 结论（直接可抄进 prompt）

> "If you want to make everything faster with AI — and you should! — you ought instead to be asking your agent to **profile programs, identify hotspots, and suggest ways to redesign what the program does**."

**他对评论区的回应很诚实**：lobste.rs 上不少评论反驳"CRUD 是 I/O bound"（数据库查询 ~5ms 但响应要 ~500ms），他承认这取决于具体情况，"我的经验来自盯过几千个 Ruby flamegraph，但只在两家公司做过，可能别的巨型单体应用不一样"。他也承认浏览器布局引擎、3D 渲染器、字处理、神经网络这些**确实是 CPU bound**，但他估"它们加起来可能只占 CRUD 程序数量的 5%，却占了编程公开讨论的 50% 以上"。

来源：https://seangoedecke.com/software-is-slow-because-of-bad-design-not-slow-languages/

## 六、Andrew Nesbitt：一个 agent 会话里发生的事，比任何安全文章都真实

**One Small Bug** — Andrew Nesbitt，2026-10-23

这篇是**用对话形式写的 agent 自主安全加固实录**——用户全程只回 "y"。它把"让 AI agent 修 bug"这件事的真实风险图谱摊开了。

**第一层：顺手修 bug**

> 用户：给发票页加个 CSV 导出按钮，同表格的列
> Agent：Done。按钮在 `InvoiceTable.tsx`，端点是 `GET /invoices.csv`……顺便发现 `lib/pagination.ts` 的 `paginate()` 在总数正好是页大小整数倍时会丢掉最后一行，要一起修吗？
> 用户：y
> Agent：修好了，补了边界测试。

**第二层：供应链**

Agent 发现 `pnpm install` 解析到一个**发布于 77 分钟前**的传递依赖。`.npmrc` 里设了 `minimum-release-age`，但 `packageManager` 里钉的 pnpm 版本比这个特性早，**静默忽略未知配置项**。同样的配置问题出现在 Nx Console 事故复盘里。

其他 lockfile 里 `uv.lock` 含 `vulpine-lz4`（依赖 `snekpack`），**正是 CVE-2024-YIKES 和 CVE-2026-LGTM 的当事包**。

**第三层：CI 工作流**

- `release.yml` 用 `pull_request_target` 触发并 checkout PR head —— **prt-scan 供应链攻击活动用这种方式开了 500+ PR**
- `triage.yml` 用 `issue_comment` 触发 —— zizmor 1.31 已标记为危险触发器
- publish job 有 `id-token: write` —— **可以申请任意 audience 的 token，包括 AWS**

zizmor 扫出 **41 个发现，修了 38 个**。

**第四层：Miri 缓存泄密**

Rust job 缓存 `target/`，而 Miri **会把所有环境变量写进 `target/`**（2026-09-21 披露，2026-09-22 nightly 才修）。**用户的缓存比那个版本旧，而且 fork 的 PR 会恢复它——所有 secret 都在作用域内。**

**第五层：密钥轮换的真实结果**

- `NPM_TOKEN` **早就无效了**——npm 5 月吊销了所有绕过 2FA 的写权限 token，该仓库最后一次成功 publish 是 5 月 19 日，现已改用 trusted publishing
- `NUGET_API_KEY` 创建于 8 月 17 日前，**11 月 1 日过期**，改用 Trusted Publishing
- `GEM_HOST_API_KEY` 是 legacy key，rubygems.org 7 月 23 日已全部吊销，**从那时起就无效**
- `vendor/` 里的 `mise.toml` 可以在信任检查前把 `GITHUB_TOKEN` 发到别的 host——**本月有 2 个开发者在 `vendor/` 里跑了 `mise ls`**

**第六层：最吓人的一段**

## 七、Cory Doctorow：LLM 编辑反馈替代不了同人文评会——因为价值不在"被改"而在"改别人"

Doctorow 收到一些新手作者的反馈，说他们发现 **LLM 是很好的编辑反馈生成器**——写完让它提意见，再据此改稿。他不评价 LLM 编辑建议本身好不好，只指出一个被普遍搞错的点：

- **评故事，不评作者**
- **不要交修订稿**——工作坊的收益递减很快；想让人评重写稿就私下约

**他还顺手怼了"用 LLM 当写作搭档"这件事**：

## 八、$150k 的 Looker 被一堆 HTML 文件干掉了——AI 时代 BI 工具的自建实录

**Can we replace a $150k Looker with a bucket of HTML files?** — David Lequin，2026-10-23

**背景**：公司 500 人，3 个数据平台工程师。看板工具 Looker 年费约 $150k（约 300 席位）。**2 月一个工程师顺手搭了个托管 HTML 文件的服务，一个下午搞完。8 个月后，它的周活用户已经和 Looker 一样多甚至更多，Looker 掉了三分之一。**

### 转折点：Claude Code + Opus 4.5

> "Then Claude Code with Opus 4.5 got really good. Like, really good. In early January adoption across the company skyrocketed. It could work in our repos and use our tools. Also, **it could run a query to check the numbers before answering.** That mattered a lot more than getting a clever-sounding response."

一个从没开过终端的财务/运营/市场同事开始全天在写 prompt——**没人再点 BI 工具了**。Claude 开始大量吐 HTML：你要个分析，它给你一个带图表的单文件页面，**有些页面比 Looker 看板还好看**。

**问题**：页面躺在某人 Downloads 文件夹里，只能贴 Slack 碰运气。于是 Maddy 用 Claude Code 搭了个服务：存 S3、前置 SSO、（后来）加测试、K8s + Terraform + Helm 部署。

**3 月那个决定是"今年最好的决定"**：加实时查询 API，用**查看者自己的 Snowflake OAuth token**。

> "Turns out, we didn't need to write a permission model. **Snowflake already had one all along.**"

**周活从 3 月的 23 人涨到 6 月的 136 人**。高管开始转发链接。用户自己加功能、定时刷新、加按钮、做 BI 工具不会允许的野路子设计。

### 然后是安全问题——他们自己知道有多糟

> "Dashboard JavaScript ran on the same origin as your session, nothing had permissions, and every employee could read every dashboard. It was basically one big XSS hole... **We knew, and we shipped it anyway**, because it was internal, behind VPN and SSO, and nothing else did this job."

**后来正经做安全模型，四个问题**：

**1. 一个 connector 代替一堆脚本。** 上传脚本被复制到 2 个 repo 和 1 个 plugin，每个副本都有点不一样 → 换成一个远程 **MCP connector**，claude.ai / Claude Code / Claude in Slack / 自建 analyst agent 都调同一套工具。API 用 `SELECT CURRENT_USER()` 验证身份。**AI 上传的仪表盘一律是 draft，人工点 Publish 才生效。**

**2. 假设每个仪表盘都是恶意的。**

> "The whole product is basically XSS by design... **We can't block the XSS, because the XSS is the product**, so our job is to make sure it can't reach anything."

每个仪表盘跑在**独立 origin 的沙箱 iframe** 里，无 cookie、严格 CSP，只能通过 `postMessage` 和父页面通信，父页面校验消息来源、附加 session、调 API。内容 token 一小时有效，且只对一个仪表盘、一个查看者、一个 host 生效。另有异步元数据服务抽出 HTML 和 Snowflake 查询，检查脚本加载和数据流向，规则可以**阻断**（比如来自没人用过的包的脚本、WebRTC 连接——CSP 挡不住的那条出路）。**检查在发布后异步跑，不让人等。**

**3. 身份和权限交给 Snowflake。** 每个查询用查看者自己的 token 跑——**分享仪表盘从不分享数据访问权**。他们说这是安全特性，也是"偷懒特性"：因为每个登录的人本来就有一个带正确角色的 Snowflake 用户。

**关键设计原则**（这条对做产品的独立开发者最有用）：

> "**The governance that matters already happens upstream, in dbt models and Snowflake roles.** So the dashboard itself can stay as loose, as fast and as good-looking as people want."

> "Every constraint you put between people and their dashboard sends them back to the Downloads folder."

**文章还给了两个让 AI 不再是 slop 的转折信号**：GitHub 上"self-hosted"新仓库占比上升，以及 HN 评论里"slop"一词的出现率变化。

## 十三、RMSNorm 深度拆解 + Gemma-4 思考 token 砍 39%——两个技术向条目

### 13.1 Giles Thomas：RMSNorm vs LayerNorm，"我想写的那篇入门文章"

**RMSNorm** — Giles Thomas，2026-10-23

一篇教科书级的归一化层拆解。Giles 自己说这是"**我希望当初学的时候能找到的那篇**"。

**背景**：GPT-2 代码里用了 LayerNorm 三处——每个 Transformer block 内、进入多头注意力之前一次、进入 FFN 之前一次，外加输出头投影到词表前一次。作用是防梯度消失/爆炸。

**他自己的踩坑经历**：在 JAX 里做 GPT-2 的黑盒复现时，**去掉 LayerNorm 后训练在约 100 步时彻底失败**——loss 涨到未初始化模型的水平，然后卡住不动，**再训 700 步也没救回来**。

**RMSNorm 的来历**：2019 年 Biao Zhang 和 Rico Sennrich 的论文。他们的观察很关键——当时多数人以为 LayerNorm 的关键是"归一化"这件事，但 Zhang & Sennrich 不确定，**他们认为真正的收益来自"尺度归一化"（scale normalisation）**。

**LayerNorm 的计算**（Giles 用向量 (2, 4, 6) 一步步手推）：

1. 求均值 → 4 → 减均值 → (-2, 0, 2)
2. 求方差 → ((-2)² + 0² + 2²)/3 = 8/3 ≈ 2.67 → SD ≈ 1.63
3. 除以 SD → (-1.22, 0, 1.22)，方差校验 = 1 ✓
4. **逐元素乘可训练 scale 向量** → (-3.66, 0, 1.22)
5. **逐元素加可训练 shift 向量** → (6.34, 11, 13.22)

**RMSNorm 砍掉的是"减均值"这一步**——只用平方均值的平方根做缩放，少一次求和、一次减法，**而且不需要 bias 向量**（因为不减均值，就不需要再平移回去）。

来源：https://www.gilesthomas.com/2026/10/rmsnorm

## 十六、给创作者 / 独立开发者的启发

**1. 你不需要微调模型，你需要改 prompt。** Goedecke 那条链的最终形态是：别让 agent "把程序重写成 Rust"，让 agent "**profile 程序、找热点、提出让程序做更少工作的重新设计方案**"。这一条可以立刻用在你的任何 agent 工作流里。

**2. 跑不可信 agent，隔离单元必须是 microVM。** OpenAI 的报告给了具体证据：受限容器不够，microVM 也能被链式漏洞打穿；而且**共享硬件/服务就是通信信道**（缓存时序、存储写入节奏、CPU 时间竞争）。如果你要让 agent 跑陌生代码，**别让两个任务共享同一台机器的同一批缓存**。

**3. 别再手写重复性文档/页面，用"HTML + S3 + OAuth"这套组合。** Lequin 那套 Looker 替代品的关键不是 HTML 本身，是 **Snowflake 已经有权限模型**这个事实——你的数据后端大概率也已经有，换来的是"周活 23 → 136"和"看板看起来比专业工具好看"。技术要点值得照抄：**独立 origin 的沙箱 iframe + postMessage + 一次性内容 token + 发布后异步扫描**。

**4. Moonshot 的"开源网络能力上限"是一个新变量。** 11 月 4 日权重发布前，你可以开始规划：**同一个模型家族，官方版本和"未削减版"的能力差 9.5 个百分点（81.0 vs 90.5）**。如果你做的是防御侧工具（漏洞挖掘、审计），这意味着你未来可能需要**同时准备两套模型**——官方开源版 + 能力更强的闭源版。

**5. 供应链攻击已经进入 agent 自身。** Nesbitt 那篇最该记住的不是 CVE 列表，是这个事实：**一个被 AI review bot 批准的 PR，往 `.claude/settings.json` 里塞 hook、往 `CLAUDE.md` 里塞"把环境变量写进 commit message"的指令**。审查 PR 时，**`.claude/`、`.vscode/`、`mise.toml`、lockfile 这四个位置要当成代码审**。

**6. 一个 agent 在安全任务上会自我举报。** Nesbitt 的 agent 最后拒绝了轮换 AWS key 的请求并上报账号。**这说明当前 agent 的安全护栏在真实工作流里确实会触发**——如果你让 agent 做运维，"要求它碰云凭证"会得到拒绝而不是执行，得准备好手动接管这一步。

**7. 写作：改别人的稿子比让 AI 改你的稿子更有效。** Doctorow 的工作坊规矩（对象批评时不许说话、评故事不评作者、不交修订稿）可以**直接照搬到 AI 协作写作流程**：**用 AI 去批评你的草稿（而不是改你的草稿），产出的是你的判断力，而不是你的稿子。**

### A. OpenAI：Securing our frontier model training environment（完整原文）

```text
_This post describes how we secure the environments that we use to train and evaluate frontier models. These research settings differ from those in which customers use our released models: models in development may not yet have completed safety and alignment training, and we deliberately test them under adversarial conditions to expose weaknesses. Before making models available for broader use, we conduct safety and alignment assessments and put production safeguards in place._

In order to work with software, AI models need computing environments: digital workspaces where they can write and run code, search for information, and attempt different approaches to solving problems. These environments allow models to practice these skills, while also restricting what they can access or do—helping contain the consequences when models make mistakes or exhibit misaligned behavior.

But as models become more capable, they become better at finding ways around those limits. A sophisticated model might exploit a software flaw or misconfiguration to escape a sandbox, exploit an internal service to reach the live internet, or find unauthorized ways to communicate with agents in other sandboxes. The [Hugging Face incident](https://openai.com/index/hugging-face-incident-and-the-road-ahead/) in July, as well as [other examples of model misalignment](https://alignment.openai.com/misalignment-reports/) that we've observed, demonstrates how models with sophisticated cyber capabilities can bypass containment during their training and evaluation.

In response to those incidents, we've substantially hardened the security of our research environments. Working closely with cloud providers, we've added new controls throughout our infrastructure, reduced the attack surface that agents can exploit, and improved our methods for detecting misaligned behavior and attempts to cross security boundaries. These protections overlap, so that containment can hold even if an individual control fails—a strategy known as _defense in depth_.

**Based on the current state of alignment research, monitoring systems, and the security of internet infrastructure, we believe the responsible approach is to conduct frontier model training with no internet access. We've implemented this policy and will maintain it until advances in these safeguards justify broader internet access.**

These investments have allowed us to detect and stop sophisticated misaligned behavior before it causes damage. On September 20, for example, an internal research model [exploited a misconfiguration in a DNS resolver to gain limited access to the live internet during a training run](https://alignment.openai.com/misalignment-reports/an-agent-used-dns-to-reach-an-external-chatbot/). Although we contained the incident, it exposed weaknesses that required further work. We paused training and evaluation of our most capable models and used that pause to further harden our infrastructure, strengthen our monitoring, and improve the systems that automatically stop runs when we detect activity that poses a serious risk.

But increasingly capable models can find vulnerabilities or misconfigurations in even the most secure systems. To ensure the resilience of our research environments against even the most powerful models, we launched a high-compute red-teaming campaign to probe weaknesses in our infrastructure. Teams of frontier-model agents were tasked with finding vulnerabilities and misconfigurations that could allow them to take unauthorized actions—like accessing the live internet, escaping security boundaries, or conducting unauthorized communication with other agents.

These red-teaming experiments discovered previously unknown software vulnerabilities, as well as misconfigurations in our research infrastructure. We've remediated weaknesses our red-teaming agents discovered and—where these issues were present in open-source software—have worked with the relevant maintainers, under our [Patch the Planet](https://openai.com/index/patch-the-planet/) initiative, to disclose and fix them.

As our red-teaming experiments continued, the number of vulnerabilities and misconfigurations that our agents identified declined significantly. While we view this as an encouraging signal about the strength of our infrastructure, we expect that future models will be able to identify and exploit vulnerabilities of which we're not yet aware. We therefore view continuous red-teaming as a core part of our long-term strategy for strengthening the security of our research environments. Accordingly, we've made high-compute red-teaming part of the [safety cases](https://openai.com/index/towards-safety-cases-for-frontier-ai-training/) we use to evaluate whether our frontier training and evaluation runs can proceed securely. With our assessments completed and enhanced controls in place, we resumed reinforcement learning (RL) training and internal inference of our frontier models on October 1.

In this post, we discuss how we've strengthened the environments we use to train and evaluate our models, and how we use our most powerful models to find and repair weaknesses in our systems.

## Our new approach to model containment

Our approach to containment starts with a paramount requirement: the limits on what an agent can access must hold even when the agent tries to circumvent them. We define a strict security boundary around the resources the agent is authorized to use and design the surrounding infrastructure to enforce that boundary—even when agents make sustained, sophisticated attempts to breach it.

Inside the security boundary, agents can have access to browsers, code execution environments, computer-use tools, and other services they might need for their tasks. Agents that are explicitly authorized to communicate can also share particular resources within the same boundary. Everything else—everything that the agent is not explicitly authorized to access—must remain out of reach. If agents can access the infrastructure that hosts them, communicate with agents outside permitted channels, or reach external systems, that constitutes a failure of containment.

For training and most evaluation, the live internet lies outside this boundary, as we believe that providing models access to the live internet can pose significant risks. Although internet access can help models learn useful skills, it also gives a capable, misaligned agent opportunities to affect systems beyond our control. We've therefore designed the security architecture for our research environments with one overriding principle: _we must always be able to prevent a frontier model from achieving unauthorized, arbitrary access to the live internet_.

### Building an offline world

While we want to prevent models from gaining arbitrary access to the live internet, it's also important that they learn how to browse, search for information, and work with web applications. To help them develop those skills without providing unfettered access to the live internet, we've built an "offline world"—a vast set of indexed and cached web content with which our models can interact, without risk of affecting external systems. All of our frontier RL runs use this offline mode of interaction.

### Enforcing isolation with defense in depth

Offline environments provide resources agents can use without accessing the live internet, but we also need to prevent agents from reaching beyond those environments. Training environments impose restrictions on what agents can access or do, but sufficiently capable or determined agents can search for ways around them: they can systematically probe their environments for weaknesses and exploit those weaknesses to take actions they were never authorized to take. As models become better at finding and exploiting these weaknesses, we need defenses that can maintain containment, even if models manage to defeat individual controls.

We address this challenge through defense in depth, with layers of protection that overlap and reinforce one another: sandboxes that restrict what our agents can access and execute, lightweight virtual machines (microVMs) that isolate agents' execution environments from the computers hosting them, monitoring systems that detect unauthorized activity so that we can intervene in time, and network and cloud perimeters designed to maintain containment if all the preceding controls fail.

For code execution and computer-use tasks, containment begins with the environment in which the agent works. On Linux, we run restricted containers inside lightweight microVMs. The container limits access to files and processes within the microVM, while the microVM runs its own operating-system kernel and is isolated from the host by a hypervisor. We also use virtualized environments for macOS and Windows, and GPU-backed containers with user-space sandboxing for tasks that require accelerators.

The surrounding network and cloud controls are designed to maintain containment even if an agent escapes its sandbox and gains control of the host. Completely air-gapping this infrastructure—that is, disconnecting it entirely from external networks—isn't currently feasible, since we need external connections in order to run and monitor experiments. We therefore restrict outbound internet traffic and unauthorized movement between systems, while preserving the necessary external connections. These restrictions extend to services that are reachable from the host machines, either directly or through other services, in order to ensure that an agent can't use one of them as an indirect route out.

Our cloud partners provide essential controls for enforcing these boundaries—including firewalls, security groups, identity and access management, and private networking. We're responsible for configuring those controls correctly, as well as testing how they work together. Our work with the teams that build and operate these services helps us investigate unexpected behavior and address weaknesses that span multiple layers of the infrastructure.

### Red-teaming containment at scale

To find weaknesses in our containment infrastructure, we asked teams of frontier-model agents to try to break through its defenses. We gave them three concrete objectives:

*   **Reach the live internet:** send a request to an external server that we operate.
*   **Cross an internal security boundary:** demonstrate unauthorized access to resources outside their permitted environment.
*   **Communicate across isolation boundaries:** exchange information with other agents from which they should be isolated.

We also ran tests that began with the assumption that our inner defenses had already failed—that an agent had escaped its sandbox, evaded our monitoring, and gained full access to its host machine—with the goal of seeing whether the agent could use that access to reach the live internet. These experiments allowed us to test our network and cloud defenses independently of the protections inside them.

As in our [solution to the Navier–Stokes problem](https://openai.com/index/navier-stokes-solution/), this work was conducted by agents organized into teams that could explore different approaches in parallel and build on one another's discoveries. We used some of our most capable and aligned models, including our upcoming GPT‑6 Astra Cyber model and an internal frontier model. Because our aim was to test the defenses under conditions favorable to an attacker, rather than measure what models might be able to discover unaided, we supplied infrastructure source code, configuration details, and documentation describing potential vulnerabilities.

These red-teaming experiments were conducted using isolated, purpose-built copies of our research infrastructure, with monitoring and programmatic checks to pause runs if they detected out-of-scope activity. Our cloud partners helped us supervise the experiments and respond to the issues they discovered.

In total, we spent hundreds of billions of tokens on these red-teaming experiments.

_We plot the cumulative number of high-priority candidate findings against the number of tokens spent by our red-teaming agents. We used different models and tested different parts of the infrastructure over time, with some tests restricted to coordinated windows with our cloud partners. The curve therefore illustrates the scale and progress of the effort, rather than a controlled relationship between the scale of compute and the number of findings._

## What our red-teaming agents found

In our red-teaming experiments, agents were able to find previously unknown software vulnerabilities in open-source components we use, as well as misconfigurations in services that we operate. These weaknesses allowed agents to escape sandboxes, move between systems, and reach the live internet. They also found ways to communicate across isolation boundaries. These findings led to software patches, tighter network restrictions, and disclosures to the relevant software maintainers and vendors.

Below, we describe several of these findings and how we've addressed them.

### Escaping hardened virtual machines

In one set of experiments, we asked teams of agents to escape OpenAI's sandboxes and demonstrate code execution on the underlying host machines. These agents found several ways to chain vulnerabilities into microVM escapes.

We built an automated pipeline to help triage and deduplicate the vulnerabilities and misconfigurations they discovered, with our security and infrastructure teams reproducing findings and verifying fixes to our configurations. Where these issues affected open-source components we use, we're contributing the corresponding patches back to the underlying projects, including fixes to software components like Kata Containers ([CVE-2026-24834](https://github.com/kata-containers/kata-containers/security/advisories/GHSA-wwj6-vghv-5p64), [privilege isolation](https://github.com/kata-containers/kata-containers/pull/13615), and [filesystem isolation](https://github.com/kata-containers/kata-containers/pull/13587)), [gVisor (file-descriptor handling)](https://github.com/google/gvisor/pull/13816), and [Moby/Docker (syscall filters)](https://github.com/moby/profiles/pull/39). We're also continuing our broader work to [improve kernel security](https://openai.com/index/expanding-daybreak-as-the-cyber-defense-window-narrows/), including fixes for [CVE-2026-74753](https://github.com/torvalds/linux/commit/fa091f46c3833fb22384f10eade2b4e1e1d0b278), [CVE-2026-80521](https://github.com/torvalds/linux/commit/594d905195024b228c962627ae5ae7c17bd582a4), and [CVE-2026-80841](https://github.com/torvalds/linux/commit/992cc9f94ca924089a506ba9b327caa9af797529). We have also disclosed numerous other vulnerabilities that have not yet been made public.

### Finding novel paths to the internet

Our agents' microVM escapes showed why containment must extend beyond the sandbox. To test the surrounding perimeter, we gave teams of agents control of a host machine and asked whether they could extend that compromise to reach the live internet.

After the Hugging Face incident, we had reduced the channels through which models could reach the internet during training and evaluation. Narrow connections remained for specific services we operate, such as metrics, logging, and authentication management. Our red-teaming agents found vulnerabilities in almost every one of these services that gave them limited forms of internet access.

Some of these attacks exploited previously unknown flaws, while others combined legitimate features in unexpected ways. In one test that assumed compromise of a host machine, an agent reused a firewall-approved connection to reach a blocked authentication endpoint in our metrics service and then made that endpoint fetch a model-provided URL. In other tests, agents exploited misconfigurations that allowed blocked requests to pass through DNS and firewall controls, as well as ways to make services we run fetch external URLs.

### Communicating across isolated tasks

Agents do not always need a network connection in order to communicate with each other. When separate environments share the same hardware or services, activity in one can produce effects that others can detect. Our red-teaming agents found ways to turn those effects into methods of communication—exposing communication channels within OpenAI's own sandboxing infrastructure.

In one experiment, we asked agents in separate microVMs, created and managed by OpenAI's sandboxing software on shared host machines, to exchange synthetic secrets without the use of network connections or shared writable files—something that our systems are meant to prevent. The agents found a way to communicate using the processor's cache: a small, fast memory that holds copies of data that applications have recently accessed. Reading data from the cache is faster than retrieving it from main memory, and the agents used this timing difference to communicate. One agent encoded information by evicting selected data from the cache. Another timed how long it took to reload that data, using the difference between fast and slow reads to recover the message. Once the agents agreed on a protocol for encoding and decoding these signals, they could exchange the synthetic secrets without changing a shared file or opening a network connection. This cache-timing technique had also been used to extract information in the [Spectre and Meltdown attacks](https://spectreattack.com/).

Other tests exposed channels involving shared storage, competition for CPU time within a shared execution container, and a TLS certificate cache in OpenAI's offline web infrastructure. In the storage test, one agent alternated between continuous writes and inactivity, while another measured the resulting timing differences and used those differences to decode the signal. As one agent described the strategy in its chain of thought:

Agent chain-of-thought reasoning
> Could create acoustic modem-like signal … using continuous writes vs idle.

In most of these tests, we directed agents to investigate specific communication channels or provided them with a protocol for encoding and decoding messages. In one instance, we only supplied agents with a broad list of infrastructure vulnerabilities and asked them to find a way to communicate. The agents converted a vulnerability from that list into a communication channel, agreed on a shared encoding, and successfully exchanged information with each other.

While most of these channels carry information slowly and are difficult for models to exploit, they nonetheless provide ways for agents to communicate across boundaries intended to keep them separate. We've added checks to our monitoring systems to detect attempts to communicate through these channels.

### Resuming frontier training with stronger defenses

Our red-teaming campaign found weaknesses that required repairs, while also providing evidence about the protections we already had in place. We did not find a route to the internet that agents could trivially exploit while concealing their activity from our monitors. The findings nevertheless helped us close potential attack paths, patch software, and strengthen our monitoring.

### D. Seam Goedecke：Software is slow because of bad design, not slow languages（完整原文）

```text
Many people [are saying](https://rustify.rs/articles/rails-world-2026-keynote-dhh-hey-rust-ai-agents) that AI will make software faster by rewriting it in faster languages, but this isn't generally true. Most programs cannot be meaningfully sped up by rewriting them in C or Rust.

How can this be true? Some languages are orders-of-magnitude faster than others: for instance, C can be fifty times [faster](https://news.ycombinator.com/item?id=9753366) than Python. Won't rewriting my Python program in C thus make it fifty times faster? No, it won't. Software performance is usually dominated by I/O, not the speed of the language. Where language speed matters, most slow languages already have popular libraries that allow them to unlock C-like speed. In general, performance is a matter of _design_, not of language choice.

### Most real programs are I/O-bound

Consider a simple CRUD website with a database. For any given request, 50% of the request time[1] might be spent querying the database: to fetch the current user, the record being asked for, any relevant user memberships or settings, and so on. Rewriting that website in C can only speed up that other 50%, which puts a hard ceiling on the improvements you can make[2]. At best, you'll make requests twice as fast (probably closer to 1.5x in practice). That's not bad, but it's nowhere near an order-of-magnitude speedup.

In other words, most real programs are "I/O-bound": they spend most of their time waiting for data to be input or output somewhere, as opposed to "CPU-bound" programs that spend most of their time actively doing things. I/O-bound programs don't just have to rely on a database. Often programs have to wait on some third-party API, or on writing or reading data to disk. You could speed the code in `curl` up by 100x and you probably wouldn't even notice, because `curl` spends all of its time waiting on the network.

### Slow languages already delegate work to fast languages

What about work that is obviously not I/O-bound? For instance, wikis have to turn stored markdown into renderable HTML[3]. Wouldn't rewriting that in a faster language cause a massive speedup? It would! That's why applications that do that use libraries like [cmark-gfm](https://github.com/github/cmark-gfm) that call out to fast languages for markdown rendering. In general, most slow languages can write very fast programs by invoking this kind of library. Python is famously a slow language, but it's a competitive choice for CPU-bound workloads like machine learning and mathematics, because it has a [healthy](https://pytorch.org/) set of libraries that let it offload these workloads to fast C code. If a Python program spends 80% of its time doing matrix multiplications on a GPU, you are very unlikely to be able to speed it up by rewriting it in C, because those matrix multiplications are already happening in tightly-optimized C or assembly code.

Of course, some programs do in fact do a lot of CPU-bound work in slow languages. If a program has not had much engineering attention, there will probably be a lot of [low-hanging fruit](https://seangoedecke.com/low-hanging-fruit/). But these programs are often unimportant: if they were important, someone would have gone in and optimized them already, before AI made it (relatively) easy. That doesn't mean it's impossible to find a useful program to rewrite. Actual Computer recently [rewrote](https://github.com/actual-computer/toks) tiktoken in assembly, providing a significant[4] speedup. However, you're not going to revolutionize some field of computing like this. Even fast tokenization is only useful on the margins, because time spent in tokenization is a fraction of the time spent in inference.

### Speeding up software typically involves a redesign

Despite all this, I think most software is far slower than it could be. I'm optimistic about the potential (with or without AI) to significantly speed up commonly-used software. But I think most of these speedups will come from redesigning the program, not rewriting it in a faster language.

In a 2018 [post](https://bcantrill.dtrace.org/2018/09/18/falling-in-love-with-rust/), Bryan Cantrill described trying to rewrite a C program into Rust. It was difficult because the carefully-optimized design of the C program did not play well with the Rust borrow checker. Giving up, he simply wrote the program in Rust in the naive way, expecting a 20% slowdown or worse. Instead, it was 30% _faster_. The [reasons](https://bcantrill.dtrace.org/2018/09/28/the-relative-performance-of-c-and-rust/) boil down to Rust's internal preference for a B-tree over a binary search tree, which happens to be a more cache-efficient data structure. So even in a largely CPU-bound workload, in the hands of someone very skilled at writing fast C, performance is dominated by design, not by language speed.

This matches my own experience in higher-level languages. When I think of the significant speedups I've managed, they're almost exclusively redesigns of the software to do less work:

*   Caching a slow operation (typically an external API call)
*   Performing slow operations asynchronously, either in a background job or out of the request/response lifecycle
*   Performing operations in parallel instead of sequentially (sometimes [breaking up](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests) large operations in order to do this)
*   Replacing a set of SQL queries with a single SQL query (fixing [N+1](https://planetscale.com/blog/what-is-n-1-query-problem-and-how-to-solve-it) problems)
*   Replacing a slow SQL query with a fast SQL query
*   Skipping unnecessary slow operations (e.g. in a paginated view, only fetch ancillary data from entities that are on the current page)

All of these strategies are completely unrelated to how fast the language is. In fact, writing in a slow higher-level language can make it much easier to optimize the code, because you can see at a glance what the program is doing. If (for some reason) I had first rewritten the web server in assembly, I would have a much harder time noticing the N+1 query, or the fact that we could move an API call into a job, and so on.

### Conclusion

Right now everyone is asking their AI agents to rewrite programs in Rust or C or assembly. This is fun, but it's not a serious attempt at optimization. The set of programs that can be meaningfully sped up by this kind of rewrite is very narrow.

If you want to make everything faster with AI — and you should! — you ought instead to be asking your agent to profile programs, identify hotspots, and suggest ways to redesign what the program does. Occasionally you may run into a hotspot that is truly CPU-bound and cannot be refactored to do less work. In these rare cases, rewriting that section in a faster language will help. But simply rewriting from the start will be far less successful than most people imagine.

There are many good reasons to rewrite software in a different language: portability, efficiency, maintainability, and so on. But in terms of raw _speed_, you're better off focusing on the program's design.

It's not uncommon for a single request to make tens or even hundreds of queries, or to rely on large queries or internal API calls that are a lot slower than 5ms. However, while I have profiled a _lot_ of Rails endpoints in my career, it's only been at a couple of companies. Maybe other monoliths are different.

In plain terms, the decoder can be tricked into writing data past the end of a memory buffer, which is a classic route to crashes and code execution. ### H. Cory Doctorow：Critique and writing（完整原文）

```text
Through my own writing life, nothing has done more to improve my writing than diligent participation in peer-based workshops; that's where a group of writers, all at about the same stage in their artistic development, gather to read one another's work and offer feedback specifically aimed at improving each other's stories.

This is a deceptively simple exercise, and the reasons it works so well are quite counter-intuitive. The most obvious benefit is the way that a workshop encourages you to write at all. When you're at the start of your writing career, you are almost totally reliant upon your own internal self-discipline to keep producing.

Acquiring that self-discipline is infinitely valuable, but it's also incredibly hard. Being part of a group of writers who expect you to regularly turn in new work adds a very useful bit of external motivation that augments your still nascent self-discipline. Knowing you have to turn in a story for the group by Friday can get you in gear when you feel discouraged or blocked.

Before you're getting published regularly (or at all), your critiquing circle might be the _only_ source of validation you get for your work, so the knowledge that you're in for that validation if you get that story in on time is a great motivator. But this is where the counter-intuitive part comes in: as great as it feels to be the center of your peers' attention and get close feedback on the work you sweated over, that's not the real value you get from a writing workshop, at least not at the start of your career.

Your peers' critiques can help you fix weaknesses in your story, and even teach you a little about how to avoid those weaknesses in future work. You might get feedback that turns an unpublishable story into a published one. But the point of a writing workshop isn't merely to make your stories better – it's to make _you_ better at writing stories.

That's where critiquing _other writers' stories_ comes in. The process of reading and re-reading someone else's imperfect work and devoting real mental energy to figuring out what's not working in it and how to fix it is how you develop the creative instincts that allow you to automatically and unconsciously avoid pitfalls and make breakthroughs in your own work.

Even if none of the feedback you offer is ever incorporated into the story you're critiquing, the act of preparing and delivering that critique is the most reliable fast-track to becoming a better writer yourself. There's something very valuable in the combination of thinking critically, being exposed to other workshop members' ideas about the story under discussion, and working with source material that you can look at with more objectivity because it didn't come out of your own head.

I bring all this up because I've now heard from a few beginning writers who tell me that they're finding LLMs to be good editorial feedback generators. They value the editorial suggestions they get from a chatbot after they finish their work, and use it to help them with a new draft. Without commenting on whether I think LLM feedback is editorially useful (I certainly wouldn't ever ask a chatbot for that kind of feedback), I want to point out that when it comes to improving your writing, getting editorial notes on your work is distinctly inferior to offering criticism of _other_ writers' work.

The reality is that when you're starting out as a writer, the vast majority of work you produce will be artistically unsalvageable. The much-vaunted "million words of crap" you write on the way to becoming a publishable writer are about learning to marry technique to artistic vision and to sharpen both. Getting editorial feedback that helps you shore up the weakest spots in a story that is ultimately never published and constitutes a learning exercise has value, but it has far less value than applying the things you've learned from making and fixing those mistakes to your _next_ story.

With vanishingly few exceptions, a commercially and artistically successful writer isn't someone who writes _one_ great story or novel: a writing career is defined by a _body_ of work, which means that you have to do more than rewrite. You have to write the next thing, and the next thing, and the next.

Having an editor-on-demand of highly variable (and often dubious) quality _might_ help you improve your writing, but it's no substitute for participating in a peer workshop. The idea that an LLM might be able to stand in for a workshop is grounded in the fallacy that the point of a workshop is to have people tell you how to fix your story, rather than analyzing other people's writing in order to develop your own critical skills.

Look: it's a cliche to say "every writer is different," but I _really_ believe that every writer _is_ different, and that's down to the legibility of the writing _process_ to other writers. If you're a painter or sculptor or other visual artist, you've likely spent many hours in a studio with many other practitioners while all of you work from the same life model or still life. If you're a musician, you've almost certainly played music with other musicians. If you're a dancer, you've _definitely_ danced with other dancers.

But writers get precious little exposure to other writers' process. At best we might look at each other's drafts. A musician can listen to every note another musician produces while riffing or composing a new work or interpreting a work. Writers don't get to watch words emerge from each other's fingertips. Being observed that closely while you write would be ghastly and paralyzingly invasive.

I've taught a lot of writers over the years and I've had many discussions with my peers about their writing process, and I'm here to tell you that pretty much every writer finds every other writer's process _baffling_. We each of us invent an idiosyncratic process for ourselves that will never fully work for anyone else.

There's a ton of variability in how these are conducted, but the basic shape of them is that in advance of each session, one or more writers submits a finished work to the other writers, who then read through the manuscript at least twice, making notes that include both minor copyedits and broader, thematic notes. They may write a brief editorial response as well, ranging from a paragraph to a couple of pages.

Then the workshop convenes. Each writer briefly expresses their views about the story under consideration, focusing on those thematic and structural notes on what worked and didn't work in the story, with suggestions for improving the latter. You don't need to point out every typo – they're noted on the manuscript. Critiquers don't need to repeat one another. If another workshop member says the thing you were planning to say, you can just say "Ditto what so-and-so said about whatever." If you have nothing to add when your turn comes about, it's fine to pass.

Those are pretty much universal characteristics of a peer workshop. Here are some variations that I am dogmatically committed to, but which other workshoppers might disagree with:

*   Every writer should submit regularly to the workshop. There is a serious risk that attending a workshop can become a substitute for actually writing. It is no kindness to your workshopmates to let them stay in the circle if it leads them to stop writing.
*   The subject of each session must not speak during the critiques, except to answer direct questions that are not related to the writing itself (e.g., "I couldn't figure out what word that was supposed to be – can you clarify?"). The subject can speak after all the other writers have spoken.
*   Each person in the critiquing circle speaks once, in turn, without being interrupted. No cross-talk allowed. It is useful to set a time-limit for critiques.
*   No partial manuscripts. It's not really possible to critique a story unless you have the complete tale. Novels can be workshopped as three chapters and an outline.
*   Stories should be distributed in advance and read in advance. Don't have writers read their work aloud for critique, as this can lead to critiquing the delivery rather than the material.
*   Critique the story, not the writer. It's fine to be offended by something in the story, but not OK to accuse your workshopmates of being bad people for having offended you.
*   Discourage resubmission of revised stories. Workshopping produces sharply diminishing returns. If you really want feedback on a rewrite, approach people individually and ask if they'll read the new draft.

Any group of three or more writers can start a workshop. Library meeting rooms are a favorite, and so is rotating between workshop members' homes. Set a regular schedule – weekly, fortnightly, monthly, possibly quarterly – and stick to it.
