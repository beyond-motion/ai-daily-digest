## 🛠️ 工程工具：Apple 终于做了开发者呼吁 20 年的事——Xcode 支持 JSON 工程文件

Xcode 27.2 发布了一项被开发者"喊了二十多年"的功能：**JSON 格式的工程文件（`.xcproj`）**。John Gruber 总结了三个开发者反应：

- Simon B. Støvring："开发者们多年来一直在呼吁更友好的 Xcode 工程格式。我也是其中之一。"
- Tony Arnold："我整个职业生涯都在等这个！🎉"
- Rob Napier："这又是一个'我们很快做了一件帮助 AI 的事，而这些年来一直不愿意帮人类做'的例子。我在整个行业都看到了这种现象。值得欢迎和感谢，但它花了'这能帮 AI'才实现，这也让人沮丧。"

**关键事实：**
- 旧格式 `.pbxproj` 不是 XML，是古老的 NeXT 风格 ASCII plist。**讽刺的是这个格式本身已经非常接近 JSON，但 JSON 和 JavaScript 都还没诞生**
- 真正的痛点不是 plist 本身，而是其中所有对象都用不透明 ID 表示——Xcode 里一个微小改动经常导致多处 ID 重排，让 git merge 几乎不可能
- Apple 在 GitHub 开源了 Swift 库和 CLI 来读写新格式
- 旧版本 Xcode 27 仍可打开新格式工程

## 🌐 开源新模型：llm-typesafe 0.1a0 + Simon Willison 发布"Jev 模型"插件

Simon Willison 发布了他为 **TypeSafe AI 的新 Jev 模型** 写的 LLM 插件 `llm-typesafe 0.1a0`。Jev 是一个专门做**结构化判断**的模型——输出 yes/no、choice、score 三种类型，而不是自由文本。

**使用示例：**

```bash
# yes/no 问题（返回 {"type":"noul","noul":0.99}）
llm -m jev 'Please refund my last payment.' \
  -s 'Does this message explicitly request a refund?'

# 多选题
cat message.txt | llm -m jev \
  -s 'Which team should handle this message? If billing and technical issues both occur, choose billing.' \
  -o answer_type choice \
  -o criteria '{"billing":"...","technical":"...","other":"..."}'

# 评分
cat report.txt | llm -m jev \
  -s 'How reproducible is the problem?' \
  -o answer_type score \
  -o criteria '["No reproduction instructions","Some instructions","Complete steps"]'
```

TypeSafe AI 的 waitlist "移动速度似乎相当快"——Simon 拿到了 API key 并立刻把它做成了 LLM CLI 插件。这是把"判断"作为一等公民的小模型思路，呼应了 Simon 在 RSS 早些时候发的另一篇："Cheaper LLM labelling"（kqr.org）。
